# SLM 端云路由：期中后进展汇报（约 10 分钟）

图片按讲的顺序编了号，讲到哪部分就打开对应的图。

---

## 1. 背景和问题（1 分钟，不用放图）

**一句话**：每个请求，是交给笔记本上的小模型（SLM），还是交给云端大模型（LLM）？

- 本地小模型：省钱、碳排低、不依赖网络，但答得不一定好。
- 云端大模型：答得好，但每次调用都有能耗、碳排和费用。
- 三个研究问题：
  - **RQ1 质量**：小模型和云端比，差多少？差在哪类题上？
  - **RQ2 成本**：本地和云端各自的延迟、能耗、碳排是多少？
  - **RQ3 路由**：用什么规则分配请求，能在质量和碳排之间取得最好的平衡？

## 2. 系统和方法（2 分钟）→ 图 `02_system_flow.png`

- 请求带上任务类型，发到 **Go 网关**，由网关决定走本地还是走云端。
- 本地用 Ollama 跑小模型：Llama 3.2 3B、Qwen3 1.7B，期中后又加了 **Phi-3.5 mini** 和 **Gemma 2 2B**。云端用 Groq 上的 gpt-oss-120b。
- 题库是 4 类任务各 100 题，共 400 题：yes/no（BoolQ）、新闻分类（AG News）、信息抽取（SQuAD）、数学（GSM8K）。
- 抽取题用两个不同家族的 LLM 评审（judge）打分，两者一致率 98–99%。

## 3. RQ1 质量（2 分钟）→ 图 `04`、`05`

- **图 04**：所有小模型在每类任务上都不如云端，但弱项各不相同：
  - Llama 和 Qwen 在分类、数学上弱。
  - Phi 数学很强（0.86），分类很弱（0.47）。
  - Gemma 正好相反：分类 0.69，数学 0.57。
- 全部走本地（Llama）准确率 74.8%，全部走云端 91.5%。
- **图 05**：用模型自己的"置信度"（token 平均对数概率）判断答没答对，效果一般，AUROC 只有 0.52–0.83。这一点决定了后面 cascade 的上限。

## 4. RQ2 成本（2 分钟）→ 图 `06`、`07`

- **图 06**：在笔记本 GPU 上，本地一次请求的碳排大约只有云端的 7%。数学题输出长，本地能耗最高。
- **图 07**：GPU 上本地很快；换到 CPU 或 Docker（模拟弱设备）就慢很多，2 核容器里每次请求要 2–8 秒，云端只要约 0.5 秒。

## 5. RQ3 路由（3 分钟，重点）

**图 `08_rq3_policies_llama.png`**：Llama 上 6 种策略的准确率、碳排和延迟。

- **task-rule**：碳排约为纯云端的一半，准确率是云端的 94%，而且是最快的策略。
- **rule+cascade**：准确率到云端的 98%，但碳排更高。
- **oracle**（理论上限）：约 75% 的请求留在本地，也能达到云端准确率。和 cascade 之间的差距说明，置信度信号是瓶颈。

**图 `09_three_models_policies.png`**（期中后新做）：换成 Phi 和 Gemma，策略排序完全一样，说明结论不只对 Llama 成立。另外，最优分配规则因模型而异：Gemma 把分类和抽取放本地，准确率从 0.875 提到 0.890。

**图 `10_rq3_embodied_carbonaware.png`、`10b_hourly_grid.png`**（期中后新做）：
- 改用逐小时电网碳强度（MISO 2024）后，结论基本不变，变化不到 1%。
- 算上隐含碳以后，本地请求碳排约 +42%，云端约 +9%；网络传输的碳排不到 1%。
- 只按碳排路由（carbon-aware）会把所有请求都留在本地，准确率掉到 0.75。所以碳排只能在质量达标之后，用来在几个选项之间做取舍。

**图 `11_network_delay.png`**（期中后新做）：云端每次多一点网络延迟，纯本地就反而最快。Gemma 只要多 0.1 秒左右就反超，Llama 是 0.1–0.3 秒，Phi 要 0.3–1 秒。我们也通过网关实测了 +300 ms 的情况，结果和模拟一致。

**图 `12_load_test.png`**（期中后新做）：请求量大的时候，到 2 请求/秒时纯本地有 76% 超时，task-rule 只有 29%，而且 task-rule 的超时全部来自 Groq 免费档的限流。

另外，Gemma 的 live 验证（真实跑路由器）和离线模拟有 98–100% 的请求路线一致，说明离线模拟可信。

## 6. 局限和结论（1 分钟）

- **局限**：
  - 云端能耗只能估算，测不到。
  - 每类只有 100 题。
  - 置信度信号偏弱。
  - 慢网络测试最后一组还差 33 题（Groq 当天额度用完了）。
- **结论**：按任务类型把请求分给本地和云端（task-rule），是质量、碳排和速度之间最好的折中；如果更看重质量，可以再加 cascade。这个结论在 3 个小模型、4 种设备上都成立。

## 名词解释

| 名词 | 意思 |
|---|---|
| SLM / LLM | 小语言模型（几十亿参数，能在笔记本上跑）/ 大语言模型（在云端跑） |
| Edge / 端侧 | 在用户自己的设备上运行，这里指笔记本 |
| Ollama | 在本地运行开源模型的工具 |
| Groq | 云端模型推理服务，我们用它调用 gpt-oss-120b |
| Gateway / 网关 | 我们用 Go 写的中间层，收到请求后决定发给本地还是云端 |
| Routing policy / 路由策略 | 决定请求去哪里的规则 |
| always-local / always-cloud | 全部走本地 / 全部走云端，作为两个对照基线 |
| task-rule | 按任务类型固定分配：yes/no 和抽取走本地，分类和数学走云端 |
| fit-rule | 按模型自动挑选"放本地损失最小"的两类任务，是 task-rule 的按模型版本 |
| cascade / 级联 | 先让本地答；如果本地"没把握"，再把题发给云端重答（两边都要付成本） |
| rule+cascade | 先按 task-rule 分配，走本地的那部分再用 cascade 兜底 |
| oracle | 理论上限：假设事先知道本地会不会答对，只在答错时才走云端。现实中做不到 |
| carbon-aware | 只看碳排：哪边碳排低就走哪边，不管质量 |
| Confidence / 置信度 | 模型输出每个词时的平均对数概率（mean log-prob），越高说明模型越"有把握" |
| AUROC | 衡量置信度能不能区分答对和答错：0.5 等于瞎猜，1.0 是完美区分 |
| LLM judge / 评审 | 用另一个大模型判断抽取题的答案对不对，因为同一个意思可能有不同写法 |
| F1 | 按词重合度给抽取题打分的传统指标，对换了说法的正确答案很苛刻 |
| gCO2e | 克二氧化碳当量，碳排的单位 |
| Carbon intensity / 碳强度 | 每度电产生多少碳（g/kWh），随地区和时间变化 |
| MISO | 美国中部电网运营商，明尼苏达州属于它，我们用它 2024 年的逐小时数据 |
| Embodied carbon / 隐含碳 | 制造设备（笔记本、服务器）时产生的碳，按使用时长分摊到每次请求 |
| Operational carbon / 运行碳 | 运行时耗电产生的碳 |
| Latency / 延迟 | 从发出请求到拿到完整答案的时间 |
| Deadline miss / 超时率 | 在规定时间内（这里一般是 2 秒，数学题 10 秒）没答完的比例 |
| Open-loop load test / 开环负载测试 | 按固定节奏发请求，不等上一个请求返回，模拟真实的高并发 |
| 429 | 云服务返回的"请求太多、被限流"错误 |
| Docker profile | 用 Docker 容器限制 CPU 和内存，模拟更弱的设备 |
| LibreHardwareMonitor | 读取 CPU 功耗的工具，用来测本地每次请求的能耗 |
| Live check | 真实运行路由器，而不是离线模拟，用来验证离线结果 |
| Replay / 离线回放 | 用已有的答题结果和测得的成本，计算各种策略的表现，不用重新跑模型 |
